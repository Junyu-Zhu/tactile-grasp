# 0b — 测试规范：阶段门控与验收标准

本文件定义每个阶段“怎样才算通过”。原则：**没有机器可读报告，就不算完成；没有标签有效性，就不能报告 metric-valid 指标。**

## G0：盘点与接口冻结

### 输入
- Stage-I force/slip checkpoint；
- Stage-II future head checkpoint；
- SPARSH encoder/backbone 配置；
- IsaacSim dataset/artifact root；
- 输入预处理规则。

### 检查
- 路径存在；
- checkpoint 能 load；
- 输入 shape、frame stack、resize、normalization、background subtraction 写清楚；
- 输出字段命名固定。

### 通过条件
生成：

- `inventory_report.json`
- `inventory_report.md`

且 `status: PASS` 或明确列出 blocking issue。

## G1：IsaacSim 模型前向烟测

### 输入
至少包含三类片段：

- no-contact；
- stable-contact；
- slip-inducing。

### 检查
- dataloader 输出 shape 正确；
- Stage-I 输出 force vector 和 `p_slip_current`；
- Stage-II 输出 `p_instability_H1/H3/H5`；
- 导出每帧 metadata + predictions；
- 无 NaN/Inf；
- 检测 raw future risk 是否饱和。

### 通过条件
生成：

- `model_forward_smoke_report.json`
- `model_forward_smoke_report.md`
- predictions csv/json

并明确结果标签：`SMOKE_ONLY` / `PROXY_ONLY` / `METRIC_VALID`。

## G2：标签有效性

### Force label 必须说明
- 单位是否为 N；
- 坐标系：world / gripper / contact / sensor；
- normal/tangential 分解规则；
- valid mask。

### Slip label 必须满足
- 接触保持；
- 使用 gripper/contact frame 中的相对切向运动；
- 排除 no-contact、intentional release、drop；
- 阈值和 timestep 可复现；
- 每帧有 `label_source` 和 `valid_for_metrics`。

### 必须判为不能 metric-valid 的情况
- world XY object motion proxy；
- success/failure label；
- contact onset；
- release/drop；
- geometry placeholder force。

### 通过条件
生成：

- `label_validity_report.json`
- `label_validity_report.md`

并明确：

- `FORCE_LABEL_VALIDITY: invalid/proxy/sim-valid`
- `SLIP_LABEL_VALIDITY: invalid/proxy/sim-valid`

只有 `sim-valid` 样本可进入后续 metric 计算。

## G3：风险校准

### 候选 score
- `p_slip_current`
- `p_instability_H1/H3/H5`
- `p_slip_current * p_instability_H1`
- `p_slip_current * max(H1,H3,H5)`
- force-only threshold
- `Ft/(Fn+eps)` / q-style risk
- 可选 logistic calibration

### 指标
- F1 / AUROC / AUPRC；
- balanced accuracy；
- false alarm rate；
- early recall；
- mean/median lead time；
- ECE/calibration curve，如数据量足够。

### 通过条件
生成：

- `risk_calibration_report.json`
- `risk_calibration_report.md`

并选出一个 deployment risk score。若 future risk 不优于 current slip，只能作为辅助诊断特征。

## G4：确定性闭环早期纠偏

### Controller 对比
- no tactile baseline；
- force-threshold controller；
- current-slip-only controller；
- gated future-risk controller；
- 可选 oracle upper bound。

### 扰动族
- stable lift；
- low friction；
- increasing lift acceleration；
- off-center contact；
- 不同 mass/friction/geometry。

### 指标
- grasp success/drop rate；
- slip event count；
- early intervention rate；
- warning/intervention lead time；
- intervention 前后 object displacement；
- max force / over-force rate；
- action count/smoothness。

### 通过条件
生成：

- `closed_loop_baseline_report.json`
- `closed_loop_baseline_report.md`

并证明 gated/selected risk controller 相对 no tactile、force threshold、current-slip-only 至少在一个核心闭环指标上有收益，且没有不可接受 over-force。

## G5：RL 增益层

### 前置条件
G4 已通过。

### 对比项
- deterministic teacher/controller；

- RL without future-risk features；

## G6：小规模真实验证准备

### 前置条件
- IsaacSim closed-loop event timeline 已存在；
- safety bounds 已定义；
- logging schema 可迁移到 UR5/Robotiq/GSmini。

### 通过条件
生成：

- `real_smoke_readiness_report.md`

要求真实测试不依赖 simulator-only oracle label，并使用 gated/calibrated risk score。

## 最小实验规模建议

G3/G4 若要进入 evaluation-ready，建议至少：

- `num_object_families >= 3`
- `num_friction_bins >= 3`
- `num_mass_or_lift_bins >= 3`
- `num_random_seeds >= 3`
- `num_trials_per_controller >= 20`

达不到时，报告必须标为 `MVP_SMOKE` 或 `PILOT_ONLY`。

## Early-correction 事件字段

每个闭环 trial 至少记录：

```json
{
  "contact_start_t": 0.0,
  "first_warning_t": null,
  "intervention_t": null,
  "slip_onset_t": null,
  "drop_t": null,
  "recovery_t": null,
  "trial_end_t": 0.0,
  "max_force": 0.0,
  "object_safe_force_limit": 0.0,
  "no_drop_after_intervention": false
}
```

派生指标：

- `warning_lead_time = slip_onset_t - first_warning_t`
- `intervention_lead_time = slip_onset_t - intervention_t`
- `early_warning_success = first_warning_t < slip_onset_t`
- `early_intervention_success = intervention_t < slip_onset_t and no_drop_after_intervention`
- `over_force_failure = max_force > object_safe_force_limit`

## 每份闭环/RL 报告必须包含的失败模式表

- future risk 饱和；
- false alarm；
- missed warning；
- late warning；
- over-force；
- no-contact false positives；
- oscillatory control；
- drop after intervention；
- proxy-label leakage。
